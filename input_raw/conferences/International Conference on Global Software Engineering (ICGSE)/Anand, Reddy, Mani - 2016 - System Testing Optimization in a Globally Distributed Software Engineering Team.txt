Abstract—this practice paper presents how a test team of a 
software engineering organization spread across three countries 
successfully optimized the system testing effort for a large mission-
critical software system that had to conform to regulatory 
requirements. Multiple releases of the system of the system have 
been delivered to customers over 
the 15 years it has been in the 
market. Each new release adde
d new features, 
which increased 
both the number of system 
test cases required and the complexity of 
the existing system tes
t cases. Hence, a complete cycle of system 
testing for every new release required more time and effort. 
However, it was increasingly difficult to justify or arrange for such 
added efforts, especially since shorter product releases were being 
demanded. This created a vicious 
cycle where the team members, 
though experienced and highly-skilled, were unable to focus on 
initiatives to improve and optimize testing. To address this issue, we 
introduced the role of a test analyst to bridge the gap between the 
test team and other key stakeholders. We were able to optimize the 
total number of system test cases and incr
ease test execution 
efficiency while ensuring conform
ance to mandatory regulations. 
The practices adapted by the team for faster test environment 
preparation, assisted automation, along with training and 
mentoring are described. 
Keywords—test management, test stra
tegy, test refactoring, 
stake holder involvement, agile, global software engineering, 
regulatory requirements. 
I.
 
I
NTRODUCTION
 
This practice paper presents the experience of a test team of 
a globally distributed software 
engineering organization in 
reducing the system testing effo
rt for a large system, without 
modifying the test specificati
ons significantly or resorting to 
additional test automation or dem
anding excessive effort from 
testers and other stake holders. Agile development 
methodology is used [1], [2].

III.
 
C
HALLENGES
 
This section lists the challenges in optimizing system 
testing. 
Legacy
: The system under test in
cluded several legacy sub-
systems that were not adequately 
testable. This ruled out use of 
extensive test automation to achieve the objective of test 
sufficiency, resulting in increased manual testing. Also, since 
multiple releases of the system had been delivered over the 15 
years it had been in the market, the suite of test specifications 
had increased significantly, needing 
additional manual testing 
effort.  
Interdependence: 
Each location tested sub-systems 
developed in that location (see figu
re1). The aim of the system 
tests is to verify the functionalit
y and validate that the sub-
systems conform to requirements. Due to the dependencies 
between the sub-systems, functionalities in other sub-systems 
that were out of scope of testing 
for a location were typically 
covered as well, resulting in duplication of test effort. 
Target environments:
 The overall system functionality had 
to be tested on different target environments that mirror actual 
deployments in customer locati
ons. Hence, it was important to

Limited benefits from appl

: 
Though test design t

Progressively increasing number and complexity of test

: Every new product rel

had a double impact on the test cases. One, new features 
increased the total number of test cases. Two, new features also 
increased the complexity of the existing test cases that were 
incrementally modified. Hence, a complete cycle of testing of 
the application required progressive

in many instances it took less effort to create a new test case 
than to find and modify a suitable existing test case from the 
large number of test cases.  
Test environment preparation
: The test environment 
preparation, which included insta

data preparation; was not only 
complex but also consumed a 
large amount of time. It accounted for about 10 percent of total 
system test effort. The procedure to 
prepare test environment 
was manual and error prone which often resulted in 
unproductive effort. 
IV.
 
M
ANAGEMENT DIRECTIVE
 
It was increasingly difficult to justify or arrange for 
increased test effort, given the growing demand for shorter 
product releases to the end customers. 
After identifying the challenges, 
the test team defined an 
approach to reduce the system testing effort and presented it to 
the management. The management agreed with the need to 
reduce the overall test effort and set
 a goal of 20 percent effort 
reduction. 
V.
 
A
PPROACH
 
The approach involved addressi
ng the challenges by 
evaluating all possibilities of re
ducing test effort while working 
within quality pr
ocesses and resource constraints - mainly time 
and effort. This excluded any 
significantly 
effort-intensive 
methods, such as rewriting all the test cases or large scale 
automation. As part of the 
approach we implemented several 
practices that are given below. The practices also served the 
purpose of bridging the gap between several stake holders of 
the project [4].  
A.
 
Detecting redundencies and uncovering potential for 
optimization 
We analyzed test specification documents that had a likely 
overlap of functionality tested 
with the aim of detecting 
redundancies and uncovering potential for optimization.  
In this phase, the feasibility to au
tomate a test case was also 
assessed. In addition, other process improvements that could 
reduce the test effort, like faster installation cycle, usage of tool 
that provides easier editing of test cases, test data preparation 
time were considered. 
B.
 
Identifying test specifications su
itable for op
timization  
While considering optimization, it 
had to be ensured that 
there was no loss of functionalit
y covered. This meant that any 
valid test step should not be bypassed as a result of the 
optimization.  
Criteria for selecting a test specification for optimization 
was an optimization potential 
of 10 percent. Optimization 
potential referred to the reduction 
in test cases possib
le without 
affecting functionality covered. Selected test specifications 
were taken up for modification.  
C.
 
Identifying other improvements  
Though test automation was to
 a large exten
t infeasible, we 
had automated bring up tests (test cases that verify the most 
basic functionality of the a
pplication). The test automation 
framework created for bring-up tests had a potential to 
automate test steps included in a few test specifications. 
Certain changes were proposed in these test specifications, to 
automate test steps that consum
ed a disproportionately large 
share of test execution effort. Automating these test steps 
assisted manual test execution, thus reducing the overall effort.  
VI.
 
P
RACTICES
 
A.
 
Technical approach  
1)
 
Optimizing when there are multiple test cases per 
requirement 
It was observed that if a test specification had two or more 
test cases for a requirement they could contain duplicate test 
steps. By selecting and analyzing such test cases, redundant 
steps between the test cases were iden
tified and removed. 
However the guidance was not considered, if the requirement 
was large enough to justify two or more test cases. Product 
owners helped test engineers assess test cases that were to be 
merged or removed. This 
practice reduced total system test 
effort by about 6 percent.  
2)
 
Same requirement traced to
 two or more test 
specifications  
Similar functionality was gett
ing tested more than once 
under certain conditions. This w
as also due to the fact that 
different testers from different locations who authored those 
test specification in different releases were unaware of the 
overlap (see table 1). We fou
nd it feasible to remove such test 
cases, which were already available in another test 
specification. It was also possible to merge such test cases, and 
test the functionality fully. Identifying and removing or 
merging such overlapp
ing test cases reduced 
the total system 
testing effort by about 1 percent.   
3)
 
Repeated test case in different test configurations 
Traditionally, some test cases 
were getting re-executed in 
all application configurations. While it was necessary to 
execute some test cases in all 
application configurations, it was 
not required for many test cases, as it did not increase system 
test coverage. Adequacy of testing in a subset of test 
configuration per test case was decided only after a discussion 
with developer and the architect. The count of test cases did 
100 not decrease in this case. However the unnecessary repeated 
execution of same test cases was avoided, which shortened the 
test execution time and reduced 
total system test effort by 2 
percent. This also help
ed in reducing the gap in the 
understanding between arch
itects/developers and testers. 
4)
 
Merging two levels of system testing 
The software requirements were divi
ded into problem level 
and solution level requirem
ents. The problem level 
requirements were those that state the intended functionality as 
a ‘problem statement’, with a description as a use case. The 
solution level requirements provide more implementation and 
application user interface details. The test cases that trace to 
problem level requirement keys 
have to cover the workflow 
level user actions while the solu
tion level test cases have to 
cover more detailed application level interactions. 
As a consequence, 2 levels of test cases were written.  
There were instances, where both the requirements were 
described in a similar way or the functionality did not mandate 
a more detailed test case. In such cases, related test cases for 
each of the levels also contained similar test steps. When such 
test cases were analyzed together redundancies were detected. 
Redundant test cases were merged after an assessment by 
product owners and testers. This has 
reduced total system test 
effort by about 2 percent.

Interface  functionality tested at two levels 
The system level testing for use case level requirement keys 
is intended for overall workflow testing. However, it is not 
appropriate to test lower level interfaces in system tests, but 
they need to be tested in the integration test level. The 
discussions held with Prod
uct owners and Testers has 
enhanced the understanding of appropriateness of a test level. 
By avoiding repeated interface system tests it was possibility to 
reduce total system test effort by about 1 percent.  
6)
 
Automation 
The application already had a test automation framework. 
An evaluation was done to 
identify the test cases that were 
suitable for automation and us
e only the existing framework. A 
group of test cases were identified 
which had the support from 
test automation framework already or required minor 
modifications. This approach facilitated 
a rapid development of 
test automation suite at system test 
level, with li
ttle effort. On 
the whole, automation reduced 
the total system 
test effort by 
about 3 percent. 
7)
 
Assisted installation and
 configuration 
Manual installation of the app
lication was effort intensive. 
The process of installation and 
configuration was a series of 
complex steps, taking up to 0.5 
person days per installation. 
Since testers typically need to install the system about 3-4 
times for one complete system 
test cycle, automating system 
installation offered promise.  In 
addition, automation had an 
added benefit of minimizing errors 
during installation, which 
required time consuming re-installation. Test automation 
engineers worked with manual testers to provide required 
guidelines to automate system 
installation. By using 
automation scripts to install th
e system reduced the total 
system test effort 
by about 2 percent.  
8)
 
Reducing the time taken
 for bring-up tests 
The bring-up tests were executed as a batch of test cases, 
which required changes to the configuration files after a test 
case is executed and before the next test case starts executing. 
After the configuration changes, several application 
programs/services need to be restarted for the changes to take 
effect. Previously, for every configuration file change, the 
entire set of application programs/services were being 
restarted, which consumed a considerable amount of time.  
Testers working with architects proposed approaches to 
optimize the time taken, by id
entifying and restarting only the 
necessary application programs/services. This required no 
changes to the existing test environment and only minor 
changes to the existing test scripts. Restarting only the 
necessary application programs/services, between two test 
cases, has shortened the time to execute the bring-up tests and 
has reduced the total system test effort by about 1 percent.

pact test specifications

in synch with other project goal
s, a prioritization of the test 
specifications taken up for up

impact of changes was done. This approach was similar to data 
mining methodology of [5], but 
with a focus on specification 
with highest impact and intende
d change. This 
also helped in 
meeting the overall

C.
 
Communication and training 
1)
 
Communication 
It is important not only to
 set a goal and make plan for 
implementation, but also to communicate the plan to the test 
team and other stakeholders. The 
test managers from different 
location meet three times a week, using conferencing tools to 
exchange data and information rega
rding the test planning, 
progress, and support requi
red from other stakeholders. 
Subsequently, they communicate 
essential details to other test 
team members.  The topic of 
test specification optimization is 
included as a main agenda of these 
meetings. In addition, the 
entire system test team meets once a week to discuss 
impediments.  
The approach and progress of the system test effort 
optimization is communicated to all test teams and also to 
other stakeholders as part of m
anagement reports.  
2)
 
Training and applying learning 
Detailed guidelines drawn
 for test specification 
optimization helped the test engineers to apply them. Test 
engineers were provided with hands-o
n training on test design 
techniques. In addition, hand
 holding by senior testers, system 
analysts, and architects also helped. This has opened an 
unexplored possibility of 
designing test cases in more 
structured way. Applyi
ng suitable test 
design techniques for 
existing and new test cases has reduced clutter of repeated test 
steps and has resulted in cleaner test cases.  
3)
 
Increasing quality focus 
As studies from Gartner [7] 
have shown, “The lack of 
testing and QA standards, as we
ll as a lack of consistency, 
often lead to business disruption,
 which can be costly.” Gartner 
also reports that “testing consumes 25% to 50% of the average 
application life cycle and often is viewed as adding no business 
value”. Adherence to quality, regulatory and organization 
quality standards is essential to 
reduce unproductive effort 
spent on testing. Recognizing th
e need, testers were provided 
the same access to team activities, portals and documentation 
as other team members. The test manager provided guidelines 
for addressing quality factors for each test cases adhering to 
ISO/IEC 25010. This approach 
provided a suitable ‘
ility
’ test 
with least possible effort.  
D.
 
Peop
le challenges 
1)
 
Evaluation of perception 
It is important not only to set a goal and make plan for 
implementation, but also to monitor the perception/acceptance 
of test engineers for the entire process.    A questionnaire on 
three parameters was prepared to
 find out if the testers: 1) were 
aware of the goals, 2) believed the approach was correct, and 
3) were confident to achieve 
the test effort reduction. Spread 
over a period of 4 months, the answers to this survey revealed 
increasingly positive perceptions, which was in line with 
results achieved. 
2)
 
Correction steps 
The approach and goals were modified based on the results 
achieved. The approach to merge similar requirements was 
replaced by removal of redundant requirements where possible. 
When the creation of automated test scripts demanded high 
efforts, the goal to automate all test cases was replaced by 
partial automation of only the effort intensive manual test 
steps.   
3)
 
Reward and motivation 
Efforts of test engineers, who ach
ieved potential reduction 
estimated and become examples for others, were appreciated 
102 by test resource managers. This also helped improve the 
interpersonal relationships be
tween manager and test team 
members. Assigning them roles to coach and mentor other test 
engineers during the optimization, increased their motivation 
levels.
