Metrics
We developed a number of key per

Work Item Count by Status
Work item count by status is intended 

to highlight bottlenecks within an 
individual sprint. It is a stacked bar 
chart where each bar represents an 

individual day in the current sprint. 

The bars are color coded by the num
-ber of work items in each state.
This particular graph was devel
-oped after interviewing software 

developers who stated that one of 
the barriers to completing items in 
a sprint was moving work items 

through the states after development 
(examples included code reviews and 
acceptance tests).

Cycle Time
Cycle time measures the amount 

of time between a work item being 
marked ready for development and 
being accepted by the business.
Cycle time primarily measures 
how much time the team spends 

working on an issue.
2By automatically computing cycle 
time, teams can rely on having more 
accurate, up-to-date data that they 
can use to help plan their sprints.
Teams within ABB use cycle time 
to help optimize their local process 
and to help with product release 
forecasts. Teams can use other anal
-yses, such as work item count by 
status, to identify possible improve
-ments in cycle time.
Prior to using the QSMP, the 
business unit manually collected 

cycle time data, aggregated it, and 
shared it via Excel spreadsheets. 

This collection was time consuming 

and was done only once per month. 
With the QSMP, cycle time is recal
-culated nightly and made available 
via a centralized dashboard.
Defect Backlog Count
The defect backlog count is measured 

as a 12-month rolling window of the 
number of opened defects waiting to 
be solved. Consumers of this metric 

can ˜lter it by product, release, pri
-ority, and source (internal versus ex
-ternal). The defect backlog count is 

presented as a KPI and provides a high-

level overview of the product™s quality.
As with cycle time, the 
defect-backlog-count metric was 
previously calculated via a manually 
updated spreadsheet that collected 

and analyzed the data.
In addition to the bene˜ts gained 
from automatically computing the 
defect backlog counts, the QSMP 

enables additional views of this data.
One of the major bene˜ts of BI 
solutions is that they allow users to 

combine disparate data sources. In 

this case, the business unit took the 
defect backlog counts and combined 
them with commits and ˜le paths 

from the source code repository.
Figure 2 shows a merged view

Each box represents a ˜le or higher-

The boxes are clickable so that the

Users can use this to target refac

Results
By migrating from a set of spread
-sheets to a centralized business solu
-tion, ABB has gained the ability to 

automatically calculate and present 

a set of actionable metrics for its var
-ious development teams.
Prior to implementing the QSMP, 
executives, managers, and team mem
-bers were only able to get monthly 
 reports generated manually by a 
team of quality personnel. We set 
out to build a dashboard solution to 

replace the quality reports and au
-tomate the process so that the data 

were updated nightly.
By combining the data collected 
with additional sources of data (such 
as source code and personnel data), 
we were able to enable additional an
-alytics that teams previously strug
-gled with.
One impact of analytics was 
 improved consistency of process 

implementation. While groups were 

following the same processes, they 
had not always used common ter
-minology and measurements. The 
software engineering analytics solu
-tion highlighted data quality issues, 

incomplete data, and inaccurate 

data. The team was able to correct 

the implementations to provide con
-sistent reporting of metrics like cy
-cle time.

When designing dashboards, we

Another key aspect of design was

The analytics solution improved
